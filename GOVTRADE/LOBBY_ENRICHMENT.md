# Lobbying Enrichment Layer

## Purpose

This document extends `GOV_TRADE.md` with a lobbying signal enrichment layer.
Read `GOV_TRADE.md` and `CONTEXT.md` fully before reading this.

The lobbying enrichment layer does not add a new pipeline. It adds a
confidence multiplier to signals already generated by `gov-trade`. When a
contract award fires a signal, the enrichment layer asks: *did this company
recently increase lobbying spend on the awarding agency?* If yes, conviction
goes up. If no lobbying data exists, the base signal is unchanged.

---

## Mental Model

```
Without enrichment:
  Contract award ($50M, new customer) → MaterialityScore: 7.5 → Signal fires

With enrichment:
  Contract award ($50M, new customer)
    + Lobbying spike on same agency 1–3 quarters prior
    → MaterialityScore: 7.5 × LobbyingMultiplier: 1.4 → AdjustedScore: 10.5
    → Higher position size, higher confidence label

  Contract award ($50M, new customer)
    + No lobbying data found
    → MaterialityScore: 7.5 × LobbyingMultiplier: 1.0 → AdjustedScore: 7.5
    → Unchanged — base signal proceeds normally

  Contract award ($50M, new customer)
    + Lobbying spend on same agency DECREASED last quarter
    → MaterialityScore: 7.5 × LobbyingMultiplier: 0.8 → AdjustedScore: 6.0
    → Mild penalty — company may not have expected this award
```

The enrichment layer never blocks a signal. It only adjusts confidence up or
down. The `RiskManagerAgent` then uses adjusted confidence for position sizing.

---

## Data Source: Senate LDA

Lobbying disclosures are filed quarterly under the Lobbying Disclosure Act.
They are publicly available via the Senate LDA bulk data API:

Base URL: `https://lda.senate.gov/api/v1/`

Key endpoints:
- `filings/` — all quarterly filings, filterable by registrant, client, date
- `filings/{filing_uuid}/` — detail for a specific filing

Each filing contains:
- `client.name` — the company that paid for lobbying
- `registrant.name` — the lobbying firm hired
- `lobbying_activities` — list of activities, each with:
  - `general_issue_code` — broad category (e.g., DEF = Defense, HCR = Health)
  - `description` — free text description of what was lobbied
  - `government_entities` — list of agencies/committees targeted
- `income` or `expenses` — dollar amount for the quarter
- `period_of_report` — which quarter this covers

Authentication: The API requires a free account and API key. This is the only
data source in this project that requires registration. Store the key as
`LDA_API_KEY` in `.env`.

Rate limits are generous (the API is designed for public access). Implement
polite rate limiting regardless.

## Architecture

### Where It Lives

The enrichment layer is a **service**, not an agent. It has no LangGraph node
of its own. It is called by `MaterialityScorerAgent` as part of scoring, after
the base materiality score is computed but before the score is written to state.

```
MaterialityScorerAgent:
    1. Compute base MaterialityResult (existing logic)
    2. Call LobbyingEnrichmentService.get_multiplier(ticker, agency)
    3. Apply multiplier → AdjustedMaterialityResult
    4. Write adjusted result to pipeline state
```

This keeps the graph shape identical to what `GOV_TRADE.md` describes. No new
nodes, no new edges.

## LobbyingEnrichmentService

### Responsibility

Given a ticker and an awarding agency, return a confidence multiplier (float)
and a human-readable rationale string.

### Interface

```python
@dataclass
class EnrichmentResult:
    multiplier: float          # 0.7 – 1.5, default 1.0 if no data
    rationale: str             # human-readable explanation
    data_found: bool           # False if no lobbying data exists for this ticker
    quarters_lookback: int     # how many quarters of data were used
    spend_delta_pct: float | None  # % change in spend on this agency, if computable
```

The service must be stateless and injectable. It should never raise — if
anything fails (API down, ticker not found, no data), it returns a neutral
`EnrichmentResult(multiplier=1.0, data_found=False, ...)` so the base signal
is unaffected.

### Multiplier Logic

The service computes the multiplier from the lobbying spend delta on the
specific awarding agency over the prior 1–4 quarters. Design decisions to make:

**What counts as the same agency?**
USASpending uses agency names like "DEPT OF DEFENSE" while LDA uses names like
"Department of Defense" or "Office of the Secretary of Defense". Build a
mapping file (`agency_lda_mapping.json`) that normalizes these. The LLM
fallback (quick model, cheap) can handle unmapped agencies.

**What time window is relevant?**
Lobbying spend from 1–3 quarters before the contract award is the most
predictive window. Spend from 4+ quarters ago is less relevant but still
directional. Weight recent quarters more heavily.

**Suggested multiplier bands** (implement these in the service, but allow
overrides via config):

| Signal | Multiplier |
|---|---|
| Spend increased > 3x on this agency, last 2 quarters | 1.5 |
| Spend increased 1.5–3x on this agency | 1.3 |
| Spend increased < 1.5x or new lobbying started | 1.15 |
| No lobbying data found for this ticker | 1.0 (neutral) |
| Spend flat on this agency | 0.95 |
| Spend decreased on this agency | 0.8 |
| Company stopped lobbying this agency entirely | 0.7 |

These are starting values informed by the thesis, not empirically validated.
Log every enrichment result with its inputs so they can be calibrated later
against actual outcomes.

**Important edge cases:**
- Company lobbies broadly (many agencies) but not specifically this one →
  treat as neutral (1.0), not negative
- Company is a first-time government contractor with no lobbying history →
  neutral (1.0), flag in rationale
- Lobbying spend exists but description mentions a competitor's contract
  vehicle → mild negative (0.85), requires LLM to parse description field

## LDA Provider

### Caching Strategy

LDA filings are quarterly — the data does not change between quarters. This
makes aggressive caching appropriate:

- Cache filing data in Redis with a TTL of 7 days
- Cache key: `lda:{ticker}:{year}Q{quarter}`
- On cache miss: fetch from API, store in Redis, return
- Store resolved ticker→LDA client name mapping in the static lookup table
  (extend `contractor_tickers.csv` with an `lda_client_name` column)

### Data Freshness

The LDA API publishes new quarterly filings approximately 45 days after
quarter end:
- Q1 (Jan–Mar) → available mid-May
- Q2 (Apr–Jun) → available mid-August
- Q3 (Jul–Sep) → available mid-November
- Q4 (Oct–Dec) → available mid-February

The enrichment service must be aware of which quarters are available. Do not
attempt to fetch data for quarters not yet published — cache a "not yet
available" result to avoid repeated failed requests.

### Bulk vs Real-time

The Senate LDA also offers quarterly bulk downloads (ZIP files with all
filings). For the initial data load (seeding historical data for all tickers
in the contractor lookup table), use the bulk download. For ongoing quarterly
updates, use the API.

Build a one-time `seed_lobbying_data.py` script that downloads and processes
the last 8 quarters of bulk data into the database. This script runs once
at setup, not as part of the live pipeline.

## New Models (`models/lobbying.py`)

`LobbyingFiling` — a single quarterly filing:
- ticker (resolved)
- quarter and year
- total spend on lobbying
- per-agency spend breakdown (derived from filing activities)
- list of lobbied agencies
- raw description text (for LLM parsing if needed)

`LobbyingSignal` — the derived signal for a specific ticker/agency pair:
- ticker
- agency
- quarters analyzed
- spend delta percentage
- trend direction (increasing / flat / decreasing / new / stopped)
- raw spend values by quarter

`EnrichmentResult` — as defined above

## Configuration

Add to `GovTradeSettings`:

```
LDA_API_KEY=...
LOBBYING_ENRICHMENT_ENABLED=true        # can disable without touching code
LOBBYING_LOOKBACK_QUARTERS=4            # how many quarters to analyze
LOBBYING_CACHE_TTL_DAYS=7
LOBBYING_MIN_SPEND_THRESHOLD_USD=50000  # ignore filings below this (noise floor)
```

`LOBBYING_ENRICHMENT_ENABLED=false` must make the service return neutral
multipliers immediately without any API calls. This allows the base `gov-trade`
pipeline to run independently during testing or if the LDA key is unavailable.

## What Success Looks Like

After 6 months of logging:

1. **Calibration check** — do signals with multiplier > 1.2 outperform
   signals with multiplier = 1.0? If not, the thesis is wrong and the
   feature should be disabled.

2. **Lead time analysis** — how many quarters before the contract award
   did the lobbying spike occur? This informs how far back to look.

3. **Agency mapping coverage** — what % of contract awards had a resolvable
   LDA agency match? Below 50% suggests the mapping table needs expansion.

The enrichment layer should be treated as a hypothesis under test, not a
proven alpha source. Log everything. Validate before increasing position
sizes based on it.
